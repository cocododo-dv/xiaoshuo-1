# 正史连续性与长篇记忆

本文描述系统当前的正史事实链、人工复核门和长篇上下文注入规则（含 2026-10-12 的「故事记忆」）。这里的“正史”指作者确认、能够追溯到当前权威正文的故事事实，不等同于规划稿、模型猜测或旧缓存。

**两层读法（2026-10-12 起）**：正史（作者核对完成的事实）是硬质检与成稿门唯一认的事实；起草提示词读的是**工作记忆**——正史之外，再加每一场当前终稿上 AI 抽出来、还没核对完的候选（作者驳回的不算）。以前候选必须等作者逐场核对才进起草，实库里一条都没核对过，后面的场次因此看不见前面写下的任何事实。现在后台每场定稿后自动抽取（`services/story_memory.py`），核对变成纠错而不是放行。

## 为什么需要独立正史层

长篇失控通常不是单纯的上下文窗口不足，而是以下对象被混成了一份状态：

- 规划中打算发生的事；
- 正文里已经发生的事；
- 模型从正文中抽出的候选事实；
- 作者确认后的权威事实；
- 已被新版正文取代的旧事实。

如果抽取结果直接进入人物状态、时间线或下一场提示词，一次错抽就会在后续章节中自我强化。当前实现因此把“抽取”“逐条裁决”和“确认清单完整”分开：模型只能产生候选，逐条接受只记录审核结论；所有候选处理完后，还必须通读当前终稿并明确确认没有漏项，系统才会在一个事务内把整场事实切换为运行时正史。

## 权威状态模型

| 对象 | 状态 | 正史（硬质检、成稿门） | 工作记忆（起草提示词） |
| --- | --- | --- | --- |
| 规划事件 | `planned` | 否（归档不再按场景卡的计划写规则事件；库里旧的 `planned` 行从不进重放） | 否 |
| 当前终稿上的正文抽取候选 | `pending`（`source_kind = prose_extraction`） | 否 | 是 |
| 作者逐条接受、场景尚未核验 | 候选为 `accepted`，事件仍为 `pending`（`canon_candidate_accepted`） | 否 | 是 |
| 场景核验后的已接受事实 | `accepted` | 是 | 是 |
| 作者拒绝的候选 | `rejected` | 否 | 否 |
| 被新版终稿取代的事实 | `superseded` | 否 | 否 |

工作记忆逐场决定认哪一份（`narrative.replay.NarrativeEventStore.working_events`）：这一场的当前终稿已经核对完成 → 只认正史；当前终稿上有还没核对完的候选 → 认这些候选；当前终稿还没有候选（新版刚归档、抽取还没跑）→ 退回这一场以前核对过的正史。

一次接受会产生不可变的单条审核 `CanonCommit`，但事件仍留在运行时之外。只有场景完整核验成功，系统才在同一事务中停用上一版正史、激活本版已接受事件、更新计划时间线兑现关系，并重建场景与章节级 `ContinuitySnapshot`。正史投影（硬质检、成稿门的连续性检查）只读取完成这一边界后的 `accepted` 事件；起草提示词的人物状态与信息差读工作记忆（见上表）。

事件回放还会独立复核：正史事件必须同时拥有有效的单条审核提交、有效的场景完成提交，并且两者都绑定当前实际正文哈希。单独篡改 `accepted`、`synced` 或快照状态不能绕过这一条件；旧式原地改文一旦造成哈希漂移，旧证明会被隔离并要求重新核验。提取器没有返回正文引文时，系统保留“无证据”状态，不会用任意正文片段代填。

场景正史完成还必须同时满足：

1. 指向当前 `FinalScene`，不能复用上一版终稿的结果；
2. 不存在待裁决候选；
3. 场景快照为 `complete`；
4. 快照引用至少一个有效的场景完成提交（`author_verification` 或 `facts_unchanged`），单条候选接受提交不能冒充全场完整；
5. 提交记录中的正文哈希与当前终稿完全一致。

旧的 `narrative_sync_status=synced` 本身不再构成证明。历史场景第一次进入新版流程时会显示待复核，需要作者完成一次提取/裁决或明确核验。

## 作者工作流

在高级模式打开 `成稿中心`，进入“正史”页签：

1. 对待提取或降级场景点击“用模型重新提取”。模型未配置时接口会明确返回 `409`，不会伪造离线结果。
2. 对每条候选核对正文证据。证据必须是当前终稿中的精确片段，否则即使点击接受也会被服务端拒绝。
3. 候选按人物的显示名与别名（人物表 / 小传 / 人物全档案里写的别名、资料库实体的名字与别名）认出指的是谁；名称存在歧义时，先选择项目内的真实实体，再接受；无法可靠归一时保持待确认。
4. 接受真实事实，拒绝误抽或无关内容。
5. 无论模型返回若干候选还是空列表，都要在完整阅读当前终稿后填写说明并执行场景核验，确认候选清单没有遗漏持久事实。

正史核对是可选的（2026-10 起）：确认定稿只要求章内每一场都有当前终稿（写齐的章在成稿中心自动列为「等你批准」；目录里旧的 `state=review` 写入同样只看正文），外加绑定作者读到的正文哈希；导出连写齐都不要求，也不看正史；正史状态照旧在成稿中心的章详情（`canon_continuity`）里报告；没核对的场，AI 抽出的事实照样进后面各场的起草（工作记忆），抽错的随时驳回。已批准的章照样可以补核——核对只写正史账本、不动正文，批准锁照旧挡正文改动。正文发生新修订后，旧版未完成候选立即失效；上一版已提交正史作为“最后一次已确认事实”保留到新版完成核验，在完成边界上再与旧时间线兑现引用一起原子失效。新版仍必须针对当前终稿重新处理，不能用旧提交证明当前正文。

人工提升正文时可以显式声明 `facts_unchanged`：来源版本已有完整、正文哈希匹配且仍有效的正史提交时，系统为新终稿建立可追溯的延续提交，而不是偷偷复用旧正文哈希。没有可沿用的（这一场第一次提升、或来源版本从没完成正史核验），提升照常成功、按 `requires_reconcile` 发布——正文成为权威正文、这一场的正史待核对，什么事实都不凭空沿用；审计里 `narrative_effect` 记实际按哪种发布，`requested_narrative_effect` 记请求里的那一种。不声明时同样需要重新提取、裁决并核验。直接调用 `carry_forward_facts_unchanged` 的来源检查照旧是 409（`CANON_CARRY_SOURCE_REQUIRED` / `CANON_CARRY_SOURCE_NOT_COMMITTED`）。

## 提取配置与失败语义

**故事记忆的后台工人**（2026-10-12，`services/story_memory.py`）：挂在运行任务巡检线程的维护任务上，每分钟看一次，有可用的模型时把 `pending_extraction` 的场按故事顺序用作者「提取」的同一条路径（整场分段）抽一遍，失败（`degraded`）的每个进程最多自动重试 3 次——模型服务暂时够不着（连不上、超时、限流、服务端 5xx）不算失败、不占次数：这一轮停下，工人从 1 分钟起翻倍退避（最多 30 分钟）再试，任何一次调用成功就清零，所以中转恢复后最迟半小时欠着的抽取、摘要与通读会自己接上；然后按故事顺序补写 / 重写章摘要（见下一节）；摘要都跟上之后，到了该编辑通读的时候顺带读一次。一轮最多调 12 次模型，真正调模型的一轮跑在自己的单线程车道里；没有模型时什么也不做。

流水线归档第 5 步另有一个可选的自动提取（只读开头约 6,000 字）：

```powershell
$env:NOVEL_SYSTEM_LLM_ENABLED = "true"
$env:NOVEL_SYSTEM_LLM_EVENT_EXTRACTION_ENABLED = "true"
```

未启用这一步时，场景保持 `pending_extraction`，由上面的后台工人接手；作者也可以从“正史”页签显式发起。作者点的「提取」按段落把整场分成几段（每段约 6,000 字）逐段读完；归档时的自动提取只读开头约 6,000 字。提示词是 `config/prompts.yaml` 的 `narrative_event_extract` 模板。供应商失败、解析失败或发送前拒绝会记为 `degraded`，不会把“没抽出来”解释成“没有事实”。模型返回空列表或若干候选都需要作者在逐条裁决后做场景级完整性确认，避免漏抽被静默放行。

**事实键的写法（2026-10-14，`services/narrative/fact_vocabulary.py`）**：硬质检只核对七种事实——死亡（`alive` = `dead`）、位置（`location`）、物品得失（`has_item:<物品>` = `held` / `lost`，每件一格）、断肢（`missing_limb`）、失能（`physical_state`：昏迷 / 失明 / 失聪 / 失语 / 瘫痪）、外貌（`appearance:hair` / `appearance:eyes` = 颜色）、能力（`ability:<能力>` = `cannot` / `can`）；别的键只进起草提示词。抽取模板 v2 让模型给每条事件选一个 `fact_kind`（结构化输出里的枚举，其余一律 `other` + 自由键名），服务端按它拼成规范键；手工补录与抽取走同一个 `normalize_fact`（「位置」→ `location`，`has_item` = `lost:断剑` → `has_item:断剑` = `lost`），意思拿不准就原样留着。「得知」「关系变化」的事实用了可查的键名会加前缀（`learned_location`），不当成这个人自己的状态。早先手写的 `has_item` = `lost:X`、`ability` = `cannot:X`、`appearance` = `hair:X` 照旧核对（`checkable_form`）。候选载荷的 `hard_check` 写明接受之后硬质检核对什么（成稿中心候选卡上的「硬质检核对」），违例带一句中文 `human_readable_reason` 给作者看。硬质检仍只读核对完成的正史，没核对的候选不拦任何正文。

## 长篇上下文注入

起草一场时，模型对已经写出来的正文知道这些：

- **人物状态与信息差**（`narrative_state` / `information_asymmetry` 段）：工作记忆截到这一场之前的重放，摘要里写人物的名字而不是内部 id；POV 知识变化按当前视角人物过滤，避免把其他人物掌握的秘密泄漏给写作者模型；最近一次核对完成的正史检查点照旧附在后面。硬质检仍读全量正史状态。
- **在场人物**：场景表的同场角色（`onstage_chars_json`）只列 POV 以外的人（POV 独自在场就是空的）；人物状态、信息差与硬质检都按 POV + 同场角色算（`character_continuity.scene_cast_ids`，2026-10-14——以前只按同场角色，POV 人物自己的状态进不了提示词、POV 加一人的对手戏没有信息差段、硬质检从不核对 POV 人物）。POV 自己得知的事只印在「POV知识边界 / POV怀疑」里，不在他的状态段再印一遍。
- **前情**（`story_so_far` 段，`services/story_memory_digest.py`）：这一章之前各章的**章摘要**——发生了什么、章末停在哪、人物的持久变化——最近 8 章全文、更早的只给一句，外加**线索台账**里至今未收的线（带埋下 / 最近推进 / 计划兑现的章与提醒，作者放下或判收的不列，最多 20 条）。还没写好摘要的章占一行。预算紧时先压成最近三章与未收的线，最后才整段省略。
- **人物**（`scene_design_context` 段，2026-10-12 起）：雪花设计背景里除了 04 角色摘要表与 06 视角故事，还有 08 **角色全档案**——POV 角色带外形、性格、处境、记忆、恐惧、希望、自我形象与人物弧，同场角色带外形、性格、人际、恐惧与人物弧。提示词要求它影响人物注意什么、想要什么、回避什么、压力下怎么反应，内层（恐惧、旧伤、记忆、自我形象、人物弧）不直接写出来。预算紧时 POV 的全档案留着、同场角色的先让路。
- **编辑意见**（`editorial_guidance` 段）：编辑通读里作者采纳的、针对这一章的意见（见下文），也进场景蓝图；硬质检不看。
- **近处**：同一章上一场的全文（风格参考优先时只留结尾），每章第一场另带上一章结尾约 800 字。

章摘要（`ChapterDigest`，节点 `chapter_digest`，模板 `chapter_digest`）在一章「写完」（各活场都有当前终稿，或作者已经往后面的章写了）之后由后台写。输入里给台账里至今还开着的线（`T1` … 编号）与后面最多 12 章的计划（章目标与每场一行），模型说出这一章推进 / 兑现了哪几条、新埋下了哪几条、哪条计划在哪章兑现；存之前编号换回稳定的 id（`<埋下它的章 id>-T<n>`）。`source_hash` 绑住整章正文、上一份摘要的内容与输入的台账：任一变了就判旧，后台按故事顺序重写，后面的章跟着判旧；作者在成稿中心「记忆」页签改过的（`origin = author`）不自动重写，只标「待更新」。它取代了 2026-06 的卷汇总（每 5 章把章汇总原文拼起来、只许当「氛围」用、只带最近一卷——几万字原文挤爆输入预算，第 11 章起前 5 章整体消失）。

**线索台账**不另存：按故事顺序把各章摘要的线索更新叠起来（`fold_threads`）。一条还开着的线 4 章没碰、后面也没计划兑现的章 → 提醒「冷了」；计划兑现的那一章写过了还没兑现 → 提醒「计划第 N 章兑现，还没兑现」。作者可以把一条线「放下」（不再提醒、不进起草）或判它「已收」（`story_thread_marks`）；标记记下当时那条线的文字，摘要重写后同一个编号换成了另一条线，标记就不再生效。

**编辑通读**（`services/story_editorial.py`，节点 / 模板 `editorial_review`，归「审稿质检」）：章摘要都跟上之后，读得到的最后一章比上一份通读往后多了 3 章、后面还有章，后台顺带读一次；作者也可以在「记忆」页签随时让它现在读。它读全书设计（一句话、五句脊柱、道德前提、长篇大纲）、主要人物的目标 / 顿悟 / 人物弧 / 恐惧与各章摘要记下的变化、各章摘要、台账里还开着的线、最近三章正文（最多三万字）、后面三章的场景结构与上一次采纳过的意见，写一段总评、问题清单（人物弧停滞、承诺没兑现、线索冷了、节奏、前后矛盾、正文偏离计划、重复；「偏离计划」的建议是改构思，作者自己改）和给后面几章的意见。意见由作者采纳（可以改字）或不采纳；采纳的进那几章各场的起草与场景蓝图，采纳、改字或撤销都会让那几章还没写的场的场景蓝图作废。新的一份存下时旧的作废，旧份里还没决定的意见随之作废，已采纳的照旧生效。

正史之外没有别的「召回」通道：2026-09 减法删除了长篇控制塔的硬锚点与伏笔生命周期等建议性叠层（全是规则与关键词，大部分从来没有数据来源），2026-09-29 的重构又删除了按字面相似度挑「相似场景」的向量检索（Chroma）。2026-10-12 用 LLM 重做了其中有用的三样：角色全档案进起草、线索台账、编辑通读。

## API

主要接口如下，所有写操作都要带 `X-Idempotency-Key`（同键同载荷重放上一次的响应）：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}` | 读取场景候选、证据和快照 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/extract` | 显式运行正文事实提取 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/candidates` | 从当前终稿精确证据手工建候选 |
| `POST` | `/api/v1/projects/{project_id}/canon/candidates/{candidate_id}/decision` | 接受或拒绝候选 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/verify` | 确认本场候选清单完整、没有漏项 |
| `GET` | `/api/v1/projects/{project_id}/story-memory` | 故事记忆：各章的章摘要与状态（`fresh` / `stale` / `missing` / `not_ready`）、线索台账、编辑通读，事实抽取还欠几场 |
| `POST` | `/api/v1/projects/{project_id}/story-memory/chapters/{chapter_id}/digest` | 存作者改过的章摘要（`base_row_id` 不是当前那一份 → 409 `CHAPTER_DIGEST_CHANGED`） |
| `POST` | `/api/v1/projects/{project_id}/story-memory/chapters/{chapter_id}/digest/regenerate` | 让 AI 重写这一章的摘要（没模型 409、调用失败 / 输出不合格 502） |
| `POST` | `/api/v1/projects/{project_id}/story-memory/threads/{thread_id}/mark` | 标记台账里的一条线：`dropped`（放下）/ `resolved`（已收）/ `open`（取消标记）；没有这条线 → 404 `STORY_THREAD_NOT_FOUND` |
| `POST` | `/api/v1/projects/{project_id}/story-memory/editorial-review` | 现在做一次编辑通读（还没有可读的章 409 `EDITORIAL_REVIEW_NOT_READY`、没模型 409、失败 / 不合格 502） |
| `POST` | `/api/v1/projects/{project_id}/story-memory/editorial-guidance/{guidance_id}/decision` | 采纳（`accept`，可带改过的 `text`）或不采纳 / 撤销（`dismiss`）一条编辑意见；已被新一份通读作废 → 409 `EDITORIAL_GUIDANCE_SUPERSEDED` |

接口会校验项目归属、当前终稿 ID、证据片段、实体归属和候选终态。针对已被替换的终稿操作会返回冲突，不会修改当前正史。

## 数据迁移

本功能由 Alembic revision `20260818_0082` 提供，故事记忆的四张表（章摘要、线索标记、编辑通读与意见）由 `20261012_0100` 加上（同时删卷汇总表；之后各版本见[数据库迁移](migrations.md)）。升级真实数据库前先停止服务并按运行安全文档完成可验证备份，再执行：

```powershell
cd backend
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic upgrade head
```

迁移不会把历史正文自动伪造为已复核正史。升级后按成稿中心列出的待处理场景逐一核验。

## 已验证与仍需实测的边界

离线回归覆盖了候选隔离、证据校验、实体歧义、按名字 / 别名认人、幂等裁决、正文换版失效、章节审批门、POV 过滤和迁移结构。这证明工程契约可重复执行，但不能证明某个真实模型的事实抽取召回率，也不能替代真实 5 章/30 章写作耐久和作者盲评。发布前仍需使用真实供应商、真实作品与固定检查点完成独立验收。
