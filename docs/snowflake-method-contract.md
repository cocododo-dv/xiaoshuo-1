# 雪花方法契约（Snowflake Method Contract）

状态：**现行契约**（2026-09-13 阶段 A–M、2026-09-15 阶段 N–S 落地后核对）。本文把构思模块的十步、场景形态、闸门与失效规则逐条对照原著，写清项目字段、哪些是硬闸门、哪些是有意的差异。代码与本文冲突时以代码为准，并回写本文。

来源：Randy Ingermanson，《How to Write a Novel Using the Snowflake Method》（第 19–20 章的十步定义与 Goldilocks 示例）与《How to Write a Dynamite Scene Using the Snowflake Method》（主动 / 反应场景、坩埚、场景分诊）。本文只借鉴方法，不复制原著文本。

## 0. 三条原则

1. **指南而非规则。** 原著反复强调步骤可跳、可回退、可改顺序。规则层只拦「缺失」与「占位」（空字段、等于提示语、含 待补/TODO），质量判断（关键词、泛泛短语、缺代价、冲突是否升级）一律只给「建议：」，不改状态、不扣分，交给 LLM 分诊与作者，并且永远可覆盖：验收门未过也可确认本步，后端闸门只守依赖顺序，规则层的「重写」也只是警告。**留白即合法**：原著的角色表满是「尚未定义」，只有主角与对手要求完整，配角留空不是缺陷，编造才是；未确认的上游草稿是工作稿，其中的留白模型不得替作者补满。
2. **提示词、归一化、诊断说同一句话。** 任何一处要求的长度、段数、字段，其余两处不得截断或判弱。数量契约（五句、五段）在生成侧以 `StructuredCountMismatch` 拒绝并重试一次，从不静默截断。
3. **设计成果必须到达写作。** 第 9、10 步写下的形态、坩埚、三拍与代价，起草、蓝图、硬软 QC、近终稿评审都能看到带标签的版本（`Scene Structure (Snowflake)` 段），不是无名节拍。

## 1. 十步对照

## 2. 场景形态

- **主动场景**：目标 → 冲突（多轮尝试受阻、逐级升级）→ 挫折。挫折**以主角衡量**：POV 是对手时，对手得手就是主角的挫折；胜利必须带主角持续支付的代价。
- **反应场景**：反应（先在身体上、先于分析）→ 两难（每个选项都有代价）→ 决定（直接生出下一场的目标）。
- **坩埚**：把 POV 困在这一场、让他不能一走了之的力量。每场必填。
- **一场挫折之后三选一**：切到另一条 POV 线、直接开下一场主动场景、或只在下一目标不明显时写反应场。反应场是少数，不要机械交替；场景类型默认主动，不按行号奇偶。
- **呈现方式**：`rendering_mode = full | summary | skip`。阶段 N 起 `summary` 对两种形态都合法——原著自己的第 1 场就是带两组三拍的叙述概述（主动场），收尾几场也是叙述——物化后篇幅带为 200–500 字，起草模板用两三段叙述性概述写这一场的三拍（主动场：目标、受阻的尝试、挫折；反应场：反应、两难、决定）；`skip` 仍只给反应场（原著的第三个选项：页面上略过，直接进下一场主动场景）：三拍照样写，物化时不建场景卡，已物化的卡回流时进回收站（改回来时取回），它的三拍整段进下一场的 `Scene Design Context`，分章节奏按 0 计。收口规则只有一处：`snowflake_steps.effective_rendering_mode`。
- **破例要知道理由**（阶段 N）：原著第 22 场明写「冲突：无」，23–25 场没有三拍——不过关也可以放行，但作者要知道理由。`exception_reason` 是作者写下的理由（迁移 `20260915_0086`）：写了理由，规则层不再把缺的三拍 / 坩埚记成缺失，完整度不扣，预检不报 `SCENE_STRUCTURE_INCOMPLETE`；结构简报渲染 `Author's exception (破例理由)` 行，起草不替作者补三拍、硬 QC 不因缺挫折 / 决定判失败、软 QC 不报 scene_shape、近终稿评审与三问按理由判；AI 分诊按「理由成不成立」判 Yes / Maybe。模型只能回显它，不能替作者写。
- **场景篇的标准进了提示词与规则层**（阶段 O / P）：好目标五条（能拍下来、装得进这一场的时间槽、对这个 POV 可能、难但不可笑、合乎价值观与志向——不再要求「有截止时间」）、好反应四条（呈现不点名、合性格、与挫折成比例）、好决定四条（逼着走、能当下一场目标、承认风险、全押）、两难落在角色 04 两条价值观的断层线上；冲突回合数没有规则（至少两轮，关键场拉长，升到顶就冲破、不平台化——不再是「2–3 轮」）；挫折是最后一次尝试、要短；反应场两难占大头、决定短、不围着计划跳舞；只解释本场的坩埚、不解释故事坩埚；POV 选损失最大的人；场景坩埚每场要新（相邻两场坩埚一字不差只提醒，不改状态）。
- **一场可以接着另一组三拍**：原著自己的场景 1 / 8 / 13 就是目标 / 冲突 / 挫折之后紧接反应 / 两难 / 决定（或反过来）。主形态的三拍是这一场的设计，另一组是可选的「次要三拍」，在主三拍之后按顺序发生，这一场以最后一个次要拍收尾；结构简报列出 `Follow-up beats` 与 `Scene ends on`，硬 QC 核验的结尾事实就是它；场景卡节拍按发生顺序拼接两组。
- **挫折可以是带代价的胜利**：非赢不可（输就是死或故事结束）时，挫折栏写胜利和它的代价，以主角衡量；干净的胜利仍不合法。
- **写完之后的分诊**：近终稿评审对每场回答「坩埚在正文里认得出来吗、设计的三拍落地了吗」，并给 Yes / No / Maybe 一句话（`scene_story_check`）。它只提示不阻断，随评审记录持久化，目录与成稿中心按场显示。阶段 R：成稿中心的三问徽章带回路——Maybe / No 可「回第 10 步」（按 `scene_id` 对到 09 的行，选中那一场改形态与三拍，再重写、再评），No 还可「标待删」（送回收站，可恢复，不真删）；自动通道在近终稿重写后本来就再评一次。
- **设计期的分诊**：AI 分诊（`snowflake_scene_triage_suggest` v3）按原著分诊判——Yes 的两条（本身是一个微型故事并给一次强烈情感体验；说得出坩埚）、No 的四条、Maybe 的七步救治，并知道概述 / 略过、带代价的胜利、次要三拍、代价只是建议、破例理由。作者的裁定四档：通过 / 需修补 / 该重写 / 待删（`cut`，作者专用，模型不能建议）。**该重写与待删不再阻断全书**：这一场不物化（不建卡，已建的卡回流进回收站，改回裁定时取回），节奏按 0 计，待删的场对相邻场来说不存在（设计上下文跳过它）；只有每一场都被裁掉 / 略过时才阻断。一场只有一条分诊记录（没带 `triage_id` 也按场对回）。

## 3. 闸门与失效

- **硬闸门**（结构物化前必须满足）：01、02、03、09、10。其余步骤缺失只产生警告。跳过需要给原因，跳过的步骤视为「已满足」进入下游上下文。阶段 M：前端的「略过此步」真的写回服务端（`generate` 带 `skip=true` + `skip_reason`，服务端记 `skipped`），必填步在前端就拒绝略过——以前只在本机打标记，后端从不知道，硬闸门于是静默卡住。
- **验收门是指南**：右栏的机器核验与人工清单只是自检；「确认本步」始终可点，后端 `approve` 才守依赖顺序（前序未确认时静默保持待批准，并在补齐后自动批准）。
- **失效（stale）的单一真相在后端**：`snowflake_staleness.FIELDS_CONSUMED` 登记每步**直接展开**的上游及其被读的字段（01→02 不含安全规则；03→04 / 05；04、05→06；05→07；04、06→08；07→09；09→10）。上游被消费的字段一改，下游确认过的步骤置 `stale` 并记 `stale_reason`；本步不消费的上游怎么改都不亮（变化经真正的下游一层层再批准来传递）；点过「已复核」的步骤在上游再改时重新亮起。09 重新批准只把内容真的变了的场景计划置 stale。前端不再保留第二套失效算法（E3 第二步已移除本地 revs 图）：只读后端的 `stale` 与 `stale_reason`，并按本步 `input_refs` 对照各上游当前的 `step_run_id` 给出「哪些上游已有新版本」的方向提示。 顶层的空值（""、null、[]、{}）与缺席同义：阶段 C 的 `rendering_mode=full`、阶段 J 的可选 `narrative_stance` 都靠这条规则保证升级前确认过的步骤在第一次原样保存时不被打回待审；真正的清空（有值 → 空）仍算改动。
- **改动已确认的步骤 = 待重新确认**：后端在步骤载荷上给 `revised_after_approval`；前端不再在停止输入一秒后自动补批准，而是显示「已改动 · 待重新确认」，等作者点「确认本步」——下游失效级联在那一刻发生，不在打字时。
- **物化之后回溯不毁正文**：01 / 02 / 03 / 05 重新确认对运行时只是提示（`scope=advisory`），已有草稿、QC、终稿全部保留，新设计经 `Scene Design Context` 段在下一次起草自然到达；09 只失效内容变了的场，07 只失效章表行变了的章里的场；10 与角色三步按场定位（原有）。
- **回溯是廉价的**：stale 横幅提供「查看上游改了什么」（按本步确认时消费的 `input_refs` 对照上游历史版本）、「按新上游重新展开」（用现在的上游材料重新生成本步，生成前留底）、「已复核」（在服务端 `accept-stale` 留痕，并把消费的上游版本刷新到当前——「仍然有效」是对现在的上游说的）。批准与复核的回包都带整份工作台，下游的失效状态即时可见。

## 4. 有意不做的事

- 不做自动出版裁决：任何评分、分诊、验收都只提示，作者拍板。
- 不给「略过」的反应场建场景卡：`skip` 只是页面上的省略，三拍照样设计并进入下一场的设计上下文（见 §2）。同理不给「该重写 / 待删」的场建卡，也不因它们阻断全书。
- 不让模型写破例理由、不让模型标「待删」：两者都是作者的决定。
- 不让模型替作者拍板意图：教练每轮蒸馏的「本步要点」只记作者说出或接受的东西，探索性提问只能记为「待定」；作者写过或改过的条目教练不能再动，作者撤下的条目教练不能复活（阶段 T）。教练、要点、方向与生成怎么分工见[雪花构思 · 教练、要点、方向与生成](snowflake-coach-and-directions.md)（阶段 U）。
- 不给章表以外的地方第二套章结构；不给前端第二套失效算法（E3 第二步已移除本地 revs 图）。
- 不复制原著文本、示例人物或桥段；Goldilocks 示例仅作为测试金标准的译写形态存在于 `backend/tests/test_snowflake_method_contract.py`。
